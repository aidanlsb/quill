# Contributing

Quill is a native macOS markdown editor. It is fast, simple, and keyboard driven. Its only job is a great markdown editing experience.

Linux `swift test` is the engine suite. It does not build the app. A change is finished when the macOS build, `Scripts/verify-quill`, and the performance gate are green.

## Performance gate

`Scripts/bench.sh` is the gate. It runs on any Mac, including Aidan's Mac, and it is what the `macos` CI job runs on pull requests.

```bash
Scripts/bench.sh                  # release build, measure, compare to Baselines/perf-macos.json
Scripts/bench.sh --bin "$bin"     # skip the build and use this Quill binary
Scripts/bench.sh doctor --bin "$bin"
Scripts/bench.sh --quick          # tiny fixtures, one pass, for wiring the harness
Scripts/bench.sh --update-baseline
```

`--quick` is not the gate. It skips the 50k and 500k notes.

The app mode is `QUILL_BENCH=1`. `QUILL_PERF=1` (printed by `Scripts/verify-quill`) is a separate, shorter measurement. The gate does not replace it.

### What it measures

Fixtures are generated by `Scripts/bench_compare.py` into `artifacts/bench/fixtures`. They are markdown, not random lines: prose, headings, lists, tables, links, and fenced code.

| Measurement | What it is |
|---|---|
| Cold launch | Process start to the first key-ready window. Five processes. |
| Open | Read, decode, load, and sync a 1k, 50k, and 500k-line note, plus a dense note. The 500k open reports the first (cold) sample and the later samples separately. |
| Keystrokes | p50 / p95 / p99 of insert and normal-mode (`x`) keys at the top, middle, and end of the huge note. |
| Motions | Repeated `j` / `k` / `w` near the top of the huge note, plus `G`, `gg`, `/quill-bench-end`, `dd`, `u`, and Ctrl-r. The first `G` is reported on its own because it lays the buffer out. |
| Restyle | One inserted character in a prose line and in a table, which is the live restyle. |
| Resize | Window width changes and the writing column is recomputed. |
| Scroll | Trackpad-style `consumeScroll` steps on the huge note. |
| Directory | Open a few-hundred-entry folder as a directory buffer. |
| Pickers | `<leader>sf` and `<leader>sg` on a repo fixture (thousands of notes, a gitignored `vendor/`). The first open is separate from the later ones. |
| Memory | Idle RSS before the huge note, and the peak RSS during the run. |

Each process discards warmups, then reports median, p95, and p99. The shell throws away one full suite first, so the file cache is warm, then the cold launches, then two more suites. The first suite processes on a fresh runner are still slowing down; the measured three start after that. It keeps the median of those runs. It does not keep the best run: a lucky sample would hide a regression.

### What fails the job

On a pull request, and on a push to any branch other than `main`, the job builds this commit and the base branch tip on the same runner and compares them. A push to `main` does not run the gate against itself. Hardware differences cancel out. `Baselines/perf-macos.json` is the recorded absolute reference for local runs and for history. The job does not fail on that file, because a different machine will not match it.

A stat fails when both of these are true:

- it is slower by more than 15% (25% for p99)
- the absolute delta is above that metric's floor

p95 is gated when a run kept at least 5 samples. p99 is gated at 15 samples. One-shot samples (cold launch across processes, the first `G`, the first picker open) are gated on the median of the repeated processes.

Floors live in `Scripts/bench_compare.py`. They exist so noise does not fail the job, while a real editing regression still does. A floor is about three times the spread of run medians (`max - min`) measured on the macOS runner. If a later job shows a larger spread, raise that floor in the same change and say why.

The numbers below are from run `39198744980` on `macos-26` (host `VirtualMac2,1`, macOS 26.6.2), three suite processes and five launches, before the discarded warmup existed. `QUILL_PERF` on that runner is not this gate: an earlier probe printed `launchToKeyMs` around 237ms, and the bench's own five launches were 121, 124, 140, 182, and 189ms (spread 68ms). Insert keystrokes that include the text view landed around 3–6ms. After the line-model merge, normal-mode `x` at the top and middle of the 500k-line note is about 300ms; identical trees on run `39200933604` moved that median by about 1ms, and moved motion p95 by 50–90ms.

The job summary and a PR comment (marker `<!-- quill-bench -->`) print the table and the run-to-run spread. Copy that table into the pull request description under `## Bench`.

### Updating the baseline on purpose

A change that is intentionally slower or faster updates the recorded file. Run the suite on the machine whose numbers you want to keep, then commit the file:

```bash
Scripts/bench.sh --update-baseline
git add Baselines/perf-macos.json
```

Do that on the macOS CI runner's class of machine when the committed numbers should match CI, or on Aidan's Mac when you want that machine's numbers in the file. Say in the PR why the baseline moved. The same-runner gate still compares against the base commit, so updating the file does not silence a regression against `main`.
